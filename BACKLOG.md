## 3. Эффект и цифры в опыте

Сейчас буллеты описывают деятельность («готовил задачи», «тестировал»), но почти нет результата.

**Зачем.** Middle отличают формулировку «делал» от «закрыл»: объём, срок, качество, влияние на соседние системы.

**Как улучшить (когда будут факты, которые можно публиковать):**

- К каждому сильному блоку (Совкомбанк, ЦПС, ТЕХНОС-К) добавить 1–3 числа: оценка в ч.ч. за период, число доработок/интеграций в проде, число сценариев автотестов, срок этапа, снижение повторных инцидентов 3-й линии после доработки.
- Формат буллета: действие → объект (система/метод/поток) → результат.
- Не выдумывать KPI. Если цифра под NDA — порядки («десятки интеграционных методов», «регресс N сценариев») без названий систем партнёров.

**Готово, когда.** В опыте есть хотя бы 5 измеримых формулировок, не только глаголы.

## 5. Hero-статистика «4 / 4 / 4»

Три одинаковые четвёрки выглядят декоративно и занижают объём (ЦПС — несколько внедрений).

**Как улучшить:**

- Развести оси: годы в анализе; число контуров/систем (страхование, ERP, КСП…); отдельная ось — не «проекты = 4».
- Либо заменить статы на доменные якоря: «страхование», «интеграции», «преподавание» — без фальшивой симметрии.
- Считать честно: параллельные роли (ИТМО + Совкомбанк) не умножают «проекты».

**Готово, когда.** Числа на первом экране отвечают на разные вопросы и совпадают с таймлайном ниже.

## 6. Навыки — чипы без глубины

Сейчас это плоский список инструментов. Python, SOA, Kafka, OpenAPI на собесе спросят «на сколько».

**Как улучшить:**

1. **Убрать или пояснить то, что не защитите за 5 минут.** SOA как ярлык лучше заменить на «интеграции REST + брокер» или убрать. Python оставить — он уже в hero и на Совкомбанке (скрипты к API и брокеру).
2. **Группы не по вендору, а по работе аналитика:** моделирование (BPMN, UML, ERD); контракты (OpenAPI, REST); данные (SQL, PostgreSQL); async (Kafka — отдельно от «пользовался Postman»); документация и трекер.
3. **Глубина в опыте, не в шкалах 80%.** В блоке Совкомбанка / ТЕХНОС-К одна фраза на навык: что именно делали с OpenAPI (писали контракт / правили / только читали) и с Kafka (топик, потребитель, идемпотентность — без секретов).
4. **Новые инструменты с якорем:** n8n и AI-практики уже в опыте Совкомбанка — в общем списке навыков только если готовы рассказать конкретный сценарий агента.
5. **Не плодить синонимы:** REST / REST-API / Swagger / OpenAPI — выбрать одну пару «REST + OpenAPI».

**Готово, когда.** Каждый тег на первом экране и в skills можно раскрыть примером из таймлайна.

## Kafka / OpenAPI на Совкомбанке — идеи, как показать глубину

Не публиковать внутренние имена топиков, партнёров и схемы полисов. Достаточно класса задачи.

Идеи для следующих итераций блока (выбрать 2–4, которые правда были):

- **Контракт:** участие в описании или согласовании OpenAPI (новый метод, ошибка, версия); отличие breaking / non-breaking; кто потребитель контракта (фронт, смежный сервис, партнёр).
- **Сценарий метода:** не «REST», а тип операции (котировка, полис, урегулирование, справочник) + синхронный вызов vs событие в брокере.
- **Брокер:** зачем Kafka, а не только REST (пики нагрузки, несколько потребителей, развязка по времени); что тестировали скриптом (публикация, чтение, повтор сообщения).
- **Качество доставки:** повторная обработка, идемпотентность, «что если событие пришло дважды» — даже на уровне постановки и тест-сценария.
- **Маппинг:** статус или сущность в КИС ↔ поле в API / в событии; кто источник истины.
- **Регресс:** сценарии автопроверок методов и цепочки «API → брокер → потребитель»; связь с оценкой в ч.ч. (сколько уходит на тест vs разработку).
- **3-я линия:** инцидент, который упёрся в контракт или «событие не тем форматом» → доработка спецификации / теста — сильный буллет без деталей клиента.
- **Артефакт в портфолио (обезличенно):** фрагмент OpenAPI (1–2 path), sequence «клиент → API → Kafka → сервис», без боевых URL.

Пока этого нет в HTML — копировать формулировки из списка выше нельзя: только то, что подтверждается работой.
